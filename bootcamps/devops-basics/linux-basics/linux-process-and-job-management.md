## Concepts

### What is a process

A process is a running instance of a program. Every process gets a unique **PID** (Process ID) assigned by the kernel when it starts. Every process (except the very first one) is started by another process, which becomes its **PPID** (Parent Process ID). This parent-child relationship forms a tree rooted at PID 1 (the init system — `systemd` on Ubuntu, which you configured in Lesson 5).

When a parent process exits before its children, the children get "re-parented" to PID 1 or to a nearby ancestor, so the tree always stays connected.

### Process states

`ps` and `top` report a single-letter state code for each process:

| Code | Meaning |
|---|---|
| `R` | Running — actively executing on the CPU or ready to run |
| `S` | Sleeping — waiting on an event (e.g. input, a timer, a lock); interruptible |
| `D` | Uninterruptible sleep — usually waiting on disk/network I/O; can't be killed until the I/O completes |
| `Z` | Zombie — the process finished, but its parent hasn't yet read its exit status; it's a dead entry, not a live process |
| `T` | Stopped — paused, usually by a signal such as `Ctrl+Z` or `SIGSTOP` |

A `+` after the state (e.g. `S+`) means the process is in the foreground process group of its terminal. Most processes you see day-to-day sit in `S` — waiting for something to do.

### `/proc` — the process filesystem

`/proc` is a virtual filesystem, generated by the kernel in memory rather than stored on disk (you saw it briefly in Lesson 2). Every running process gets a directory `/proc/<PID>/` containing files that expose its live state:

| Path | Contains |
|---|---|
| `/proc/<PID>/status` | Human-readable summary: state, PPID, memory usage, UID/GID |
| `/proc/<PID>/cmdline` | The exact command and arguments used to launch it |
| `/proc/<PID>/environ` | The process's environment variables |
| `/proc/<PID>/cwd` | Symlink to the process's current working directory |
| `/proc/<PID>/exe` | Symlink to the actual executable binary running |
| `/proc/<PID>/fd/` | Symlinks to every file descriptor (open file, socket, pipe) the process holds |

Tools like `ps` and `top` don't have special kernel access — they simply read and parse files under `/proc`. Anything they can show you, you can read yourself directly.

### `ps` — snapshot of processes

`ps` prints a one-time snapshot of processes. It supports two option styles that can be mixed on Ubuntu: BSD-style (no dash, e.g. `ps aux`) and UNIX-style (with dash, e.g. `ps -ef`). Both are common; you'll see both in the wild.

`ps aux` columns: `USER`, `PID`, `%CPU`, `%MEM`, `VSZ`, `RSS`, `TTY`, `STAT`, `START`, `TIME`, `COMMAND`.

`ps -ef` columns: `UID`, `PID`, `PPID`, `C`, `STIME`, `TTY`, `TIME`, `CMD` — note it shows `PPID` directly, which `aux` does not.

`ps -o` lets you pick exactly the columns you want, in any order.

### `top` / `htop` — live process monitor

`top` refreshes its view every few seconds and shows a summary header (uptime, load average, task counts, CPU/memory usage) above a sortable process table. `htop` is a friendlier, color, mouse-aware alternative with the same underlying data — often not installed by default, but easy to add with `apt` (Lesson 7).

**Load average** (three numbers, e.g. `0.52 0.38 0.21`) is the average number of processes that were running or waiting for CPU time, over the last 1, 5, and 15 minutes. A single-core machine is "fully loaded" at 1.00; a 4-core machine can sustain up to 4.00 before processes start queuing for CPU.

### Signals

A **signal** is a limited, asynchronous message the kernel (or another process) delivers to a process. The process can catch and handle most signals, ignore them, or let the default action happen — except for `SIGKILL` and `SIGSTOP`, which the kernel enforces directly and the target process cannot intercept or block.

The three you'll use constantly:

| Signal | Number | Default effect | Can the process catch/ignore it? |
|---|---|---|---|
| `SIGHUP` | 1 | Terminate (historically: "the controlling terminal hung up") | Yes |
| `SIGTERM` | 15 | Terminate gracefully | Yes — process can clean up first |
| `SIGKILL` | 9 | Terminate immediately | No — kernel forces it, no cleanup |

`SIGTERM` is the polite request: "please shut down." A well-behaved program catches it, closes files, saves state, then exits. `SIGKILL` is not a request — the kernel removes the process immediately with no chance to clean up. Always try `SIGTERM` first; reach for `SIGKILL` only when a process is unresponsive to `SIGTERM`.

### Job control

Your shell can track multiple commands started from the same terminal session as **jobs**. A job is either running in the **foreground** (has control of the terminal, you can't type new commands until it exits) or the **background** (runs independently, terminal is free).

`nohup` additionally protects a background process from `SIGHUP` — the signal the shell sends to its children when the terminal session itself closes. Without `nohup`, closing your SSH session would kill anything you left running in the background.

### Scheduling priority: `nice`

Every process has a **nice value** from -20 (highest scheduling priority) to 19 (lowest). A higher nice value means the process is more "nice" to others — it yields the CPU more readily. The kernel's scheduler uses this as a weighting hint, not a strict guarantee, when deciding which runnable process gets the CPU next. Lowering the nice value (toward -20) requires root privileges, since it lets a process claim more CPU than default at everyone else's expense.

## Commands / Syntax Reference

| Command | Purpose | Example |
|---|---|---|
| `ps aux` | List all processes, BSD style | `ps aux` |
| `ps -ef` | List all processes, UNIX style (shows PPID) | `ps -ef` |
| `ps -o` | Custom columns | `ps -o pid,ppid,stat,cmd -p 1234` |
| `pgrep` | Find PIDs by name/pattern | `pgrep -f nginx` |
| `pstree` | Show process tree | `pstree -p` |
| `top` | Live process monitor | `top` |
| `htop` | Friendlier live process monitor | `htop` |
| `kill -l` | List all signal names/numbers | `kill -l` |
| `kill` | Send a signal to a PID | `kill -15 1234` |
| `pkill` | Send a signal by process name | `pkill -f myscript.py` |
| `killall` | Send a signal to all processes with an exact name | `killall -9 python3` |
| `&` | Run a command in the background | `long_script.sh &` |
| `jobs` | List jobs in current shell | `jobs -l` |
| `fg` | Bring a job to the foreground | `fg %1` |
| `bg` | Resume a stopped job in the background | `bg %1` |
| `nohup` | Protect a command from SIGHUP after logout | `nohup long_script.sh &` |
| `nice` | Start a process with a given priority | `nice -n 10 ./task.sh` |
| `renice` | Change priority of a running process | `renice -n 5 -p 1234` |

## Examples / Walkthrough

```bash
# --- ps: snapshots of running processes ---
ps aux | head -n 10                    # BSD-style: USER PID %CPU %MEM ... COMMAND
ps -ef | head -n 10                    # UNIX-style: UID PID PPID ... CMD

# find your own shell's PID and its parent
echo "My shell PID: $$"
ps -o pid,ppid,stat,cmd -p $$

# custom columns, sorted by memory usage (largest first)
ps aux --sort=-%mem | head -n 6

# --- pgrep / pstree: searching and visualizing ---
pgrep -f systemd                       # PIDs of anything matching "systemd" in the full command
pgrep -u "$(whoami)"                   # all PIDs owned by current user

pstree -p $$                           # tree rooted at your shell, with PIDs shown
pstree -p 1 | head -n 20               # top of the whole system tree (rooted at init)

# --- /proc: reading process state directly ---
cat /proc/$$/status | head -n 5        # state, PPID, memory, for your own shell
cat /proc/$$/cmdline                   # exact command line that started it
ls -l /proc/$$/fd                      # open file descriptors

# --- top: interactive monitor (run this one live, not scriptable) ---
top
# inside top:
#   P            sort by %CPU (default)
#   M            sort by %MEM
#   k            prompts for a PID, then a signal, to kill interactively
#   q            quit
# header line 1 shows load average: 1-min, 5-min, 15-min

# --- job control: background a long task, then manage it ---
sleep 300 &                            # start in background, shell prints [1] <PID>
jobs                                   # -> [1]+  Running    sleep 300 &
jobs -l                                # same, but also shows the PID

fg %1                                  # bring job 1 to foreground (now blocks the shell)
# press Ctrl+Z to stop (not kill) the foreground job
# shell prints: [1]+  Stopped    sleep 300
jobs                                   # -> [1]+  Stopped    sleep 300

bg %1                                  # resume job 1, but keep it running in background
jobs                                   # -> [1]+  Running    sleep 300 &

# --- nohup: survive terminal disconnect ---
nohup sleep 300 &                      # SIGHUP-proof; output goes to nohup.out by default
disown -h %1                           # also remove it from this shell's job table (optional)

# --- signals: graceful stop first, force only if needed ---
sleep 500 &
PID=$!                                 # $! holds the PID of the most recent background job
kill -l                                # list every signal name/number the system supports

kill -15 "$PID"                        # SIGTERM: ask it to terminate gracefully (default signal)
kill "$PID"                            # same as above — SIGTERM is kill's default

sleep 500 &
PID=$!
kill -9 "$PID"                         # SIGKILL: force-terminate, no cleanup, last resort

pkill -f "sleep 500"                   # signal by matching the command line instead of a PID
killall sleep                          # signal every process named exactly "sleep"

# --- nice / renice: CPU scheduling priority ---
nice -n 10 sleep 200 &                 # start with lower priority (value 10, less urgent)
ps -o pid,ni,cmd -p $!                 # NI column shows the nice value

renice -n 5 -p "$!"                    # change priority of the already-running process
# lowering the nice value below 0 requires sudo, since that raises priority above default
sudo renice -n -5 -p "$!"
```

## Common Pitfalls

- **Confusing SIGTERM and SIGKILL** — `kill -9` looks like the "strong" version of `kill`, so people reach for it first. But SIGKILL gives the process zero chance to save state or close files cleanly, which can corrupt data (e.g. a database mid-write). Always try `kill -15` (or plain `kill`) first, and only escalate to `-9` if the process ignores it after a few seconds.
- **`kill` on the wrong PID** — PIDs get reused after a process exits. A PID captured in a variable a while ago (e.g. from `$!`) may now belong to a completely different process. Always double-check with `ps -p <PID>` before killing, especially in scripts.
- **Forgetting a background job dies with the terminal** — starting `command &` without `nohup` means the process receives SIGHUP and terminates the moment your SSH session or terminal closes. Use `nohup command &` (or, once you reach Lesson 5's territory again, a systemd unit) for anything that must outlive the session.
- **`killall` matches by exact process name, not by pattern** — `killall python` only matches processes whose command name is literally `python`; it will not match `python3` or a script invoked with a full path unless the name matches exactly. Use `pkill -f` for pattern/substring matching against the full command line.
- **Mistaking a zombie for a stuck process** — a `Z` state process is already dead; it holds no resources except its exit status entry. You cannot kill a zombie (there's nothing left to signal). The fix is to deal with its parent, which is failing to reap it — often by restarting the parent.
- **Assuming `renice` needs the same syntax as `nice`** — `nice -n 10 command` sets priority when *starting* a process; `renice -n 5 -p PID` changes it for one *already running*. Mixing up `-n` meaning ("nice increment" vs "new nice value") is a common source of confusion, though both use `-n` for the target value.

## FAQ

**Q: What's the difference between `ps aux` and `ps -ef`?**
A: Same information, different historical option conventions (BSD vs UNIX System V) and slightly different columns — `-ef` shows `PPID` directly, `aux` shows `%CPU`/`%MEM` directly. Both work on Linux; pick whichever columns you need.

**Q: Why can't I kill a zombie process?**
A: A zombie has already terminated — it's just an entry in the process table holding its exit code until the parent calls `wait()` to read it. There's no running process left to receive a signal. Fix the parent (often by restarting it) so it reaps its children properly.

**Q: What does `Ctrl+Z` actually do?**
A: It sends `SIGTSTP` to the foreground job, which pauses (stops) it — the process stays in memory in state `T`, doing nothing, until you resume it with `fg` (foreground) or `bg` (background). It's different from `Ctrl+C`, which sends `SIGINT` and typically terminates the process.

**Q: Why does my background job stop when I close the terminal, even though I used `&`?**
A: `&` only backgrounds the job within the current session — it does not protect it from `SIGHUP`, which the shell sends to all its jobs when the session ends. Use `nohup command &` to also block SIGHUP.

**Q: What's the difference between `kill` and `pkill`?**
A: `kill` takes a PID (or PIDs) and is the most precise — you must already know the PID. `pkill` takes a process name or pattern (with `-f`, matched against the full command line) and signals every matching process, which is convenient but riskier if your pattern is too broad.

**Q: Can a regular user lower another user's process's nice value or kill their processes?**
A: No. A regular user can only send signals to (and renice) processes they own. Affecting another user's process requires `sudo`/root, same as raising your own process's priority above the default (nice value below 0).

**Q: What does load average actually mean on a multi-core machine?**
A: It's the average count of processes wanting CPU time, not a percentage. A load average of 4.0 means "4 CPU-hungry processes on average" — whether that's a problem depends on how many cores you have. Load 4.0 on an 8-core machine is fine (50% headroom); load 4.0 on a 2-core machine means processes are queuing.

## Practice / Exercise

**Core:**
1. Start `sleep 300 &` in your terminal. Use `jobs -l` to find its job number and PID, then use `ps -o pid,ppid,stat,cmd -p <PID>` to confirm its state.
2. Use `pstree -p $$` to see your shell and this sleep process in the tree.
3. Practice job control: bring the sleep job to the foreground with `fg`, stop it with `Ctrl+Z`, confirm its state is `T` via `jobs`, then resume it in the background with `bg`.
4. Send it `SIGTERM` using `kill` and the PID (not `%1`), and confirm with `jobs` or `ps -p <PID>` that it's gone.
5. Start a second `sleep 300 &`, note its PID with `$!`, and kill it directly with `kill -9`. Explain in your own words why you'd normally avoid jumping straight to `-9`.
6. Start `nohup sleep 300 &`, then run `disown -h %1`. Explain what protection `nohup` gives that plain `&` does not.
7. Run `top`, sort by `%MEM` (press `M`), identify the top memory-consuming process, and read the load average from the header. State whether the machine looks under load, given how many CPU cores it has (check with `nproc`).
8. Start `nice -n 15 sleep 200 &` and confirm its nice value with `ps -o pid,ni,cmd -p $!`.

**Stretch:**
